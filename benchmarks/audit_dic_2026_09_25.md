# Revue approfondie DIC et identification alternée — 25 septembre 2026

## Périmètre et preuves

Lecture de l’alternance, intégration isotrope, préparation pixel/Q4, solveurs CG
et Gauss–Newton local, chaîne séquentielle, exports et configuration du cas.
Les solveurs de production n’ont pas été modifiés pendant cet audit.
Les reproductions `audit_dic_consistency.py` donnent les mêmes résultats sur
CPU et CUDA ; les JSON associés conservent les observations. Ce script démontre
les défauts actuels, ce n’est pas une suite de tests d’acceptation.

## Défauts confirmés, par priorité

### P1 — Le raffinement local ne minimise pas le même objectif que le CG

Sources : `numerics/global_cg.py:257-260,284` ;
`numerics/local_gauss_newton.py:413-448` ; `pipelines/sequence_platehole.py:180-190`.

Le CG utilise une **moyenne** photométrique ; les équations locales utilisent des
**sommes** de contributions pixel. La chaîne transmet pourtant le même
`reg_strength` aux deux. Pour un support fixe de N pixels, le rapport entre
régularisation et image du local est donc réduit d’un facteur N par rapport à
celui du CG. La valeur absolue dépend du support courant, mais l’incohérence est
algébrique, indépendante du solveur linéaire ou du GPU.

De plus, le CG pondère une arête par (w_i+w_j)/2 ; le local utilise w_i seul.
Avec deux nœuds, déplacements x=[0,1] et poids [1,3], les gradients sont
[-2,+2] pour le CG contre [-1,+3] pour le local. Cette seconde différence
n’intervient pas avec les poids nodaux tous égaux à un du cas courant.

Enfin, les balayages locaux n’ont ni test de décroissance du coût commun ni
arrêt sur `tol` : ils effectuent exactement `n_sweeps`. Un raffinement peut donc
dégrader la solution CG sans diagnostic. Corriger la normalisation et les poids,
puis accepter les mises à jour sur le même objectif et le même support.

### P1 — La perte de pixels peut améliorer artificiellement le coût DIC

Source : `numerics/global_cg.py:239-261`.

Le masque de validité dépend du déplacement testé, puis le coût est renormalisé
sur les pixels restants. Reproduction : coût **1,5625 → 0** simplement en faisant
sortir le pixel difficile ; le pixel restant est inchangé. Armijo ne protège pas
contre ce phénomène car il compare ces deux coûts à supports différents.

L’alternance corrige déjà ce problème via `fixed_support_photo`, mais le CG DIC
ne bénéficie pas de cette protection. Fixer le support au début d’un problème,
ou formuler explicitement le coût des occultations ; ne pas récompenser leur
suppression silencieuse.

### P1 — Décalage d’un demi-pixel selon la bibliothèque d’interpolation

Sources : `numerics/global_cg.py:218-226` ;
`numerics/local_gauss_newton.py:274-284`.

La convention du projet place le centre du pixel à (i+0,5,j+0,5). Les chemins
bilinéaire interne et cubique retranchent 0,5 ; le chemin `dm_pix` transmet les
coordonnées directement. Avec une rampe 4×4 et le point (1,5,1,5), l’interne
retourne **5**, `dm_pix` **7,5**, et `dm_pix` avec correction **5**.

Conséquence : le problème effectivement échantillonné change selon les
bibliothèques installées. Ce défaut concerne le mode linéaire ; la configuration
actuelle emploie le mode cubique. Une translation pure peut masquer cette erreur
car référence et image déformée sont décalées ensemble. Tester aussi une
variation spatiale de déplacement et la cohérence des diagnostics.

### P1/P2 — Non-finis et absence de données mal signalés

Sources : `numerics/global_cg.py:456-466`,
`numerics/local_gauss_newton.py:355-356`, `physics/discrepancy.py:117-126`.

- Une image non finie produit un gradient NaN. Après refus de la recherche
  linéaire, `alpha=0` ne protège pas `disp + alpha*direction` : 0×NaN=NaN.
  La reproduction retourne un déplacement non fini. Il faut conserver
  explicitement l’ancien déplacement en cas de refus et signaler la cause.
- Le RMS local vaut **0 avec zéro pixel valide**. Le calcul de discrepancy a
  la même convention de dénominateur et peut donc afficher un faux résultat
  parfait. Retourner un statut invalide et un RMS non interprétable.
- Les résultats CG ne distinguent pas explicitement convergence, budget épuisé
  et recherche linéaire échouée ; `n_iters` ne suffit pas à interpréter un arrêt.

### P2 — Le script DIC du cas sélectionne le CPU

Sources : `IdentVirual/sequential_dic.toml:43-47`,
`pipelines/sequence_platehole.py:252`, `io/app_utils.py:10`.

`jax_preferred="cpu"` est bien consommé par le lanceur. L’identification GPU
mesurée auparavant ne signifie pas que la DIC séquentielle exploite le GPU.
Tester une configuration GPU explicite dans un nouveau processus, en séparant
préparation, kernels et exports. Ne pas changer aveuglément toute la DIC en
float64 : la précision mécanique requise n’impose pas celle des intensités.

## Optimisations prioritaires : mémoire et temps

### 1. Supprimer ou remplacer la construction séquentielle pixel–nœud

Sources : `mesh/pixel_sampling.py:92,507-529`.

Le constructeur lance un `lax.scan` pour incrémenter un compteur pour chacune des
4×Np incidences. Une boucle compilée reste séquentielle : ce n’est pas une bonne
utilisation du GPU. Il construit systématiquement des tables denses
Nn×degré_max, même pour le CG et l’alternance qui n’utilisent pas ce gather local.

**Mesure CUDA**, 4 096 pixels synthétiques, 512 nœuds, 16 384 incidences :

| Construction | Médiane, 3 répétitions |
|---|---:|
| Chemin actuel, compilation exclue | 287,56 ms |
| Tri stable NumPy puis transfert GPU | 2,64 ms |
| Rapport | **108,99×** |

Les tables d’indices, de poids et de degrés sont équivalentes, vérifiées avant
chronométrage. Le cas synthétique utilise des incidences aléatoires ; aucun gain
sur la préparation complète du maillage réel n’en est déduit.
Le prototype est `audit_dic_preparation.py`. Le constructeur reçoit déjà les
indices sous forme NumPy : le tri hôte est ici une option simple. Pour le solveur
local, comparer ensuite un assemblage par pixel/scatter au gather dense.
Mémoire des deux tables principales : Nn×degré_max×(4+taille_du_flottant) octets.

### 2. Éviter les recalculs après une correction acceptée

Source : `IdentVirual/alternating_identification.py:267-275,411`.

La recherche linéaire calcule le suffixe, puis chaque acceptation appelle
`checked_evaluation`, qui reconstruit et réintègre **tout** l’historique pour
rafraîchir les états. Sur la validation précédente : 57 acceptations, donc
57 rafraîchissements complets supplémentaires. Faire retourner les états et
forces nécessaires par l’évaluation acceptée, ou rafraîchir seulement le suffixe.
Il faut mesurer le compromis entre sorties/buffers supplémentaires et calcul économisé.

Le chemin de gradient prépare encore la cinématique et assemble les forces pour
l’ensemble des images, même lorsque l’intégration du préfixe est sautée. Le
`where` remplace les forces du préfixe après assemblage. Une vraie API de suffixe
avec orientation initiale mise en cache est une piste plus profonde ; éviter
une compilation distincte par longueur de suffixe sans mesurer son amortissement.

### 3. Réduire les intermédiaires de différentiation

Sources : `mechanics/isotropic_history.py:58-119`,
`IdentVirual/alternating_identification.py:278`.

Le précédent benchmark mesurait environ **311 Mio** de temporaires compilés pour
le gradient implicite. Tester un checkpoint/remat de l’étape temporelle et une
fonction « coût uniquement » accumulant l’équilibre dans le scan. Conserver une
fonction séparée produisant les champs pour cache/export. La remat échange du
calcul contre de la mémoire ; aucun gain chiffré nouveau n’a été mesuré ici.

### 4. Les transferts matériau ne sont pas encore des scalaires

Source : `IdentVirual/alternating_identification.py:304`.

SciPy reçoit le résidu complet et la Jacobienne (m×3). Sur le cas réel,
1 436 nœuds intérieurs, 19 images : m=54 606, donc **1,67 Mio transféré par
nouveau point matériau** pour r et J en float64. Le cache fun/jac évite le doublon,
mais pas ce transfert. Il reste aussi des synchronisations par bool/float dans
la recherche linéaire et le calcul des coûts image.

Une optimisation bornée à trois variables pourrait recevoir coût, Jᵀr et JᵀJ
réduits sur GPU. Attention : les équations normales dégradent le conditionnement.
En présence de paramètres peu identifiables, préférer une réduction QR ou une
stratégie amortie contrôlée et conserver les diagnostics de rang. Ce changement
modifie le solveur d’optimisation ; il exige une comparaison de trajectoire/convergence.

### 5. Libérer les cartes d’image après export

Sources : `batch/mesh_based.py:197`, `methods/mesh_based.py:172`,
`io/config.py:133`, `pipelines/sequence_platehole.py:214-216`.

`keep_results=True` conserve les résultats et leurs cartes complètes sur device.
Les 19 cartes float32 de ce cas représentent à elles seules **167 Mio**, en plus
des images, champs et buffers. Garder les champs nodaux nécessaires au NPZ et
libérer les cartes après leur export. `keep_results=False` existe, mais désactive
actuellement le NPZ global : préserver cet usage avec un stockage incrémental.

Les PNG, VTI et NPZ compressés sont activés et exécutés dans la boucle : séparer
leurs temps du solveur et permettre un post-traitement différé. Si CG et local
sont chaînés, le calcul des déformations nodales est fait à chaque étage ; il
peut être reporté sur la solution finale lorsque l’intermédiaire n’est pas requis.

### 6. Réduire le nombre d’itérations plutôt que seulement leur coût

Source : `IdentVirual/alternating_identification.py:380-385,423`.

L’alternance utilise une descente de gradient dans 18 modes, sans préconditionnement.
La SVD orthonormalise spatialement la base, pas la courbure de l’objectif. Une
approximation Gauss–Newton ou L-BFGS dans cet espace réduit peut accélérer la
convergence ; à mesurer sur un même critère d’arrêt, pas sur trois passages fixes.

La stationnarité du gradient projeté n’est pas explicitement exigée par le
critère global (petits changements de déplacement, paramètres et coût). De plus,
`gradient_tolerance` porte sur le déplacement maximal induit par la direction,
pas sur une norme brute du gradient. Clarifier cette convention et enregistrer
les deux grandeurs. Un faible changement peut provenir d’un pas trop petit.

## Points scientifiques à confirmer, distincts des bugs reproduits

- `force_residual` impose l’équilibre nodal intérieur et des résultantes verticales
  aux bandes. Les nœuds de bord libres ne sont pas contrôlés individuellement.
  Si le contour correspond à une véritable surface libre, ajouter sa condition
  de traction nulle ; si le contour coupe la matière, cette condition serait
  incorrecte. Vérifier cette distinction avant toute modification.
- Les 18 modes limitent les corrections spatiales ; aucune accélération ne permet
  de corriger une localisation hors de cet espace. Étudier enrichissement et
  stabilité des paramètres en augmentant les modes.
- L’accord entre kernel isotrope et référence ne prouve pas la convergence en
  sous-incréments : tester 1/2/4/8 sur chargements non proportionnels et décharges.
- La tolérance Newton 10⁻¹³ est fixe et le backtracking évalue six candidats à
  chaque itération ; un arrêt anticipé global est envisageable. Mesurer d’abord
  résidus, nombre d’itérations et précision des sensibilités avant de relâcher
  les tolérances. Le point le plus lent pilote actuellement tout le lot.
- Lecture RGB : la DIC générale moyenne les canaux, l’alternance sélectionne le
  premier. Sans effet sur les TIFF monochromes actuels ; harmoniser avant RGB.

## Ordre recommandé

1. Unifier coordonnées, support, coût global/local et statuts numériques.
2. Retirer les gathers inutiles et remplacer leur scan de préparation ; valider GPU.
3. Réutiliser les états acceptés, libérer les cartes, mesurer le pic mémoire réel.
4. Tester remat et réduction des transferts matériau.
5. Comparer les optimiseurs sur le **temps jusqu’au même critère de convergence**.
